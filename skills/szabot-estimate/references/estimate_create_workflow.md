# 评估单创建工作流（createEvaluation）

> 🚫 **严格使用限制**：本工作流**仅适用于"创建/新建评估单"场景**。当且仅当用户明确表达了创建新评估单的意图时，才可加载并执行本文件。

> 💡 **说明**：创建评估单仅生成评估单实例（包含上会主题、决策日期等基础信息）。如需补充或修改评估单的详细字段数据，请使用「修改/更新评估单」工作流（`estimate_update_workflow.md`）。
>
> 📎 **文件衔接**：若用户在创建时附带了文件（策划书、评估报告等），本工作流创建成功后将**自动衔接** `estimate_update_workflow`，用文件内容填充评估单字段，无需用户手动发起第二轮操作。

---

## 全局执行规则

1. **底层操作静默**：MCP 调用过程不向用户展示，只呈现业务层面的信息。
2. **枚举展示约束**：向用户展示选项时，只展示中文名称。
3. **参数确认必须执行**：提交前**必须**向用户展示完整参数并获得明确确认，**禁止跳过此步骤**。
4. **文件上下文检测**：在 Step 1 收集参数时，同步检测用户是否附带了文件（策划书、评估报告、合同等）。若检测到文件，记录 `has_file_context = true` 及文件路径/引用，供 Step 4 判定是否自动衔接 update workflow。

---

## Step 1：收集创建参数

从用户输入中提取以下参数：

| 参数 | 必填 | 说明 | 可选值 |
|------|------|------|--------|
| **项目 ID** | ✅ | 关联的项目 | 用户提供或从上下文获取 |
| **上会主题** | ✅ | 评估类型 | 立项评估、开机评估、简单报备、立项+开机、提前锁定、成片采买 |
| **会议子类型** | ✅ | 会议形式 | 定期会议(3)、临时线上决策(5) |
| **最晚决策日期** | ✅ | 格式 YYYY-MM-DD | 用户提供 |
| **报备类型** | 条件必填 | 仅上会主题为"简单报备"时 | 主创/成本变更、商务条款变更、其他 |

**自动提取策略：**
1. 项目 ID — 从上下文获取（如之前查看过的项目）或用户提供；若用户提供项目名称，调用 `kb_search` 查找 ID
2. 上会主题 — 用户输入关键词匹配（如"立项" → 立项评估）
3. 会议子类型 — 用户输入数字或名称匹配
4. 决策日期 — 从用户输入提取日期，统一为 `YYYY-MM-DD`；支持"下周五"等自然语言表达

**缺失参数处理：**
- 必填参数缺失 → 一次性列出所有缺失项和可选值，请用户补充
- 不逐个追问

---
> 🛑 **CHECKPOINT**: 收集完参数后，必须展示参数确认表，等待用户明确确认后才可执行创建。
---

## Step 2：参数确认

将收集到的参数展示给用户确认：

```
📝 即将创建评估单：

| 参数 | 值 |
|------|-----|
| 项目 ID | XXXX |
| 上会主题 | XXXX |
| 会议子类型 | XXXX |
| 最晚决策日期 | YYYY-MM-DD |
| 报备类型 | XXXX（仅简单报备时显示） |

确认创建请回复"确认"，如需调整请直接说明。
```

**用户回复处理：**
- 用户确认（"确认"/"好"/"可以"/"OK"）→ 进入 Step 3
- 用户要求调整 → 修改对应参数，重新展示确认表
- 用户取消 → 终止流程

---

## Step 3：调用 createEvaluation 创建

> 静默执行，不向用户展示工具名和参数。

```bash
mcporter call szbotprojectformal createEvaluation --args '{
  "projID": <项目ID>,
  "meetingState": 100,
  "meetingSubtype": <会议子类型>,
  "subject": "<上会主题>",
  "decisionDeadline": "<YYYY-MM-DD>"
}'
# 仅简单报备时，args 中增加 "reportType": "<报备类型>"
```

**参数映射：**

| 用户输入 | 参数值 |
|---------|--------|
| 定期会议 / 排队池 / 3 | `meetingSubtype: 3` |
| 临时线上决策 / 非会议评估 / 5 | `meetingSubtype: 5` |
| `meetingState` | 固定为 `100` |

**异常处理：**

> 按 `mcp_call_rules.md` §4 的错误分类与重试策略执行。

| 情况 | 错误类型 | 处理 |
|------|---------|------|
| 网络超时 / 后端不可用 | 网络失败 | 自动重试 3 次（2s→4s→8s），全部失败后告知用户 |
| 权限不足 | 权限问题 | 不重试，引导用户检查项目权限或联系管理员 |
| 项目 ID 不存在 | 业务逻辑 | 自动尝试用项目名搜索正确 ID 后重试 1 次；否则提示用户确认 |
| 参数值不合法（如日期格式错误） | 业务逻辑 | 自动修正格式后重试 1 次；修正失败则引导用户提供正确值 |
| 评估单已存在（重复创建） | 业务逻辑 | 不重试，告知用户已有评估单并提供其 ID 和链接 |
| 后端 Schema 校验未通过 | Schema 校验失败 | 重新获取最新参数约束，修正后重试最多 3 次；仍失败则展示具体校验错误 |

## Step 4：反馈结果 + 文件衔接判定

**成功：**

```
✅ 评估单创建成功！

| 信息 | 值 |
|------|-----|
| 项目 ID | XXXX |
| 评估单 ID | <返回的 rocID> |
| 上会主题 | XXXX |
| 会议子类型 | XXXX |
| 最晚决策日期 | YYYY-MM-DD |

🔗 评估单链接：https://szgate.szabot.internal/x/r/doto9awl4o?applyId=<返回的 rocID>
```

### 4.1 文件衔接判定

创建成功后，检查 `has_file_context`：

| 条件 | 行为 |
|------|------|
| `has_file_context = true` | 告知用户"检测到附带文件，将自动为您填充评估单字段"，然后**自动衔接** `estimate_update_workflow`（见 §4.2） |
| `has_file_context = false` | 展示引导语："如需补充或修改评估单的详细字段数据，请使用「修改评估单」功能。" |

### 4.2 自动衔接 estimate_update_workflow

> ⚠️ 衔接时必须**完整读取** `references/estimate_update_workflow.md`，严格按其步骤执行。

衔接参数传递：
- `apply_id` = 刚创建成功返回的 `rocID`
- `task_key` = `base_info_collection`（固定值）
- 内容来源 = **文件**（直接确定，无需再走 Step 1.2 的来源判定）
- 文件路径/引用 = Step 1 中记录的文件信息

衔接后，从 `estimate_update_workflow` 的 **Step 2** 开始执行（跳过 Step 1，因为 `apply_id` 和内容来源已确定）：
1. Step 2：获取当前数据 + Schema + 读取/解析文件（并行）
2. Step 3：根据 Schema 从文件内容中提取数据
3. Step 4：调用三方接口 resolve
4. Step 5：组合最终数据 + 🛑 CHECKPOINT 展示 diff + 等待用户确认
5. Step 6：执行更新 + 反馈

> 📌 **衔接铁律**：自动衔接不意味着跳过 CHECKPOINT。update workflow 的 Step 5 必须展示修改预览并等待用户确认，**禁止自动提交**。

**失败：**

```
❌ 创建失败
错误信息：[MCP 返回的错误详情]
建议：[根据错误类型给出修复建议]
```

> 创建失败时不触发文件衔接，优先处理创建错误。
