## 概述

本工作流**仅适用于创建影库项目草稿**，具体流程为：
- 用户输入内容数据（影库视信息）
- 加载固定的 Schema 文件（category = 2，电视剧）
- 依照 schema 规范解析、补全、验证数据
- 最终调用对应的 MCP 工具提交数据

## 全局执行规则（执行纪律）

> ⚠️ 以下规则在整个会话期间**始终生效**，不因步骤切换而豁免。

1. **步骤追踪**：每轮回复开头必须以内部注释形式标注当前步骤，格式为：`[当前步骤: Step X — 步骤名称]`
2. **单步执行**：每轮回复只推进一个步骤。完成当前步骤后停止，等待用户输入，**禁止在同一轮回复中执行多个步骤**。例外：Step 1（告知类型）和 Step 2（加载 Schema）均为静默步骤，可与 Step 3 在同一轮执行。
3. **禁止跳步**：即使用户一次性提供了所有信息，也必须按 Step 1 → 2 → 3 → … 顺序逐步确认。
4. **回退处理**：用户要求修改已完成步骤的内容时，回退到对应步骤重新执行，已通过验证的其他字段保持不变。
5. **枚举展示约束**：向用户展示枚举选项时，只展示 `label`（中文名称），**禁止展示 `value`（数字/代码值）**。错误示例：`连载中(1)`。
6. **批量提示约束**：所有待确认问题（多结果选择、未找到、必填缺失等）必须**一次性汇总展示**，禁止逐条打断用户。
7. **Schema 忠实约束**：所有字段名、枚举值、类型均以加载的 Schema 文件为唯一事实来源，不得凭记忆猜测或编造字段。
8. **参考文件按需加载**：`references/field-types.md` 仅在进入 Step 3 时加载，之前的步骤不得提前加载，避免上下文膨胀。
9. **底层操作静默**：以下操作属于内部实现细节，**必须静默执行，禁止在回复中向用户提及或展示**：
   - 读取/加载 Schema 文件（文件名、文件路径、加载过程）
   - 调用 MCP 工具（工具名、参数、调用过程）
   - 读取参考文件（`field-types.md`、`draft_create_workflow.md` 等）
   - 解析 Schema 结构（字段属性、behavior 类型、内部分支逻辑）
   - 向用户展示时只呈现**业务层面**的信息（字段名称、选项、验证结果等），不暴露底层技术实现
10. **最大化自动识别**：尽可能从用户已提供的所有信息（自然语言、文件、上下文）中自动提取字段值，**只有无法提取或存在歧义时才向用户询问**，禁止逐字段追问。

## Step 1：告知 Category

当前仅支持**电视剧**类型，category 固定为 `2`。

在回复中告知用户当前内容类型为"电视剧"，**无需等待用户确认，直接继续执行 Step 2**。

**处理要点：**
- 仅告知用户"当前为电视剧类型"，不等待用户回复
- category 值、Schema 文件名等内部细节不对用户可见（遵守全局规则第 9 条）
- 告知后在同一轮回复中直接执行 Step 2（静默加载 Schema）并进入 Step 3

## Step 2：加载 Schema

> 本步骤静默执行（遵守全局规则第 9 条），不向用户展示任何加载过程。

直接读取 `references/tv_long_schema.json`（包含全部字段：基础 + 外部查询），无需用户选择。

将读取到的内容作为本次会话的 schema，解析 schema 结构，重点关注每个字段的：
- `name`：字段名
- `label`：字段中文名，用于向用户展示
- `type`：结构类型（`string` / `number` / `boolean` / `array` / `object`）
- `behavior`：行为类型（`enum` / `external` / 无），决定数据获取方式
- `required`：是否必填
- `format`：格式约束（如 `date`），仅 `string` 类型携带
- `enum_values`：`behavior: enum` 时的合法值列表
- `properties`：`type: object` 时的子字段列表（递归结构）
- `array_item`：`type: array` 且无 behavior 时的元素类型描述
- `mcp_tool` / `mcp_params_template`：`behavior: external` 时的查询工具与参数模板
- `result_path`：`behavior: external` 时，指定从 MCP 返回值中定位数据数组的路径（如 `"data.data"` 表示 `response.data.data`）
- `result_field` / `result_fields`：`behavior: external` 时，基于 `result_path` 定位后的数组元素，提取所需字段的映射配置
- `display_fields`：`behavior: external` 时，多结果展示给用户的字段列表（可选，详见 `references/field-types.md`）
- `condition`：条件字段，表示该字段仅在依赖字段满足特定值时才生效（详见 `references/field-types.md`）

按以下规则对每个字段确定处理方式：

```
有 behavior: enum     → 枚举处理（Step 3.1）
有 behavior: cascade  → 级联枚举处理（Step 3.2）
有 behavior: external → 外部查询（Step 3.3）
type: object / array，无 behavior → 结构类型处理（Step 3.4）
其余                  → 普通输入（Step 3.4）
有 condition          → 先走 Step 3.5 判断是否激活，再进入对应分支
```

**异常处理：**
- 若 Schema 文件读取失败，告知用户并终止流程

**本步骤为静默步骤，加载完成后直接进入 Step 3，无需等待用户确认。**

## Step 3：收集并解析用户输入

> ⚠️ **进入本步骤前，必须先读取 `references/field-types.md`，再开始处理任何字段。**

### 核心原则：最大化自动识别，最小化用户打扰

**优先从用户已提供的所有信息中尽可能多地自动识别和提取字段值**，包括但不限于：
- 用户在本轮或之前轮次中输入的自然语言文本
- 用户上传或粘贴的文件内容（如策划书、立项书、表格等）
- 对话上下文中隐含的信息

**自动提取策略：**
1. **遍历 Schema 中所有字段**，逐一尝试从用户已有信息中匹配提取
2. **枚举字段**：用户输入中出现的关键词与 `enum_values` 的 `label` 做模糊匹配（如"长剧"→"长剧"，"独播"→"独播"）
3. **级联枚举字段**：识别任意层级的关键词，自动补全完整路径
4. **外部查询字段**：识别人名、公司名等关键词，自动触发查询
5. **普通字段**：从上下文中提取项目名称、集数、简介等
6. **条件字段**：先判断依赖字段的值（可能刚被提取），再决定是否激活

**只有以下情况才向用户询问：**
- 该字段为必填，且无法从已有信息中提取
- 提取结果存在歧义（如枚举匹配到多个、外部查询返回多条）
- 所有可提取的字段处理完毕后，仍有必填字段缺失

**禁止逐字段询问用户**。应一次性处理完所有字段，将已自动填充的结果和需要用户补充的问题在 Step 4 统一展示。

每个字段按 `type` + `behavior` 组合确定处理分支：

```
behavior: enum     → 3.1 枚举处理
behavior: cascade  → 3.2 级联枚举处理
behavior: external → 3.3 外部查询
type: object / array（无 behavior）→ 3.4 结构类型处理
其余（普通输入）    → 3.4 普通字段处理
有 condition       → 先走 3.5 判断是否激活，再进入对应分支
```

### 3.1 枚举字段（`behavior: enum`）

按 `field-types.md` 中的枚举规则处理（两种写法、匹配策略、多选、serialization 等）。

**workflow 层面要点：**
- 用户输入无法匹配时，列出所有 label 供用户选择（遵守全局规则第 5 条：不展示 value）
- 匹配失败的字段加入待确认队列，在 Step 4 统一提示

### 3.2 级联枚举字段（`behavior: cascade`）

按 `field-types.md` 中的级联枚举规则处理（逐层识别、向上补全、serialization 序列化、边界处理等）。

**workflow 层面要点：**
- 只选了父级未选子级时，加入待确认队列，在 Step 4 统一提示补选
- 存在歧义时，展示所有路径供用户确认

### 3.3 外部查询字段（`behavior: external`）

**执行原则：先静默处理所有字段，收集全部问题，最后统一提示，不中途打断。**

数据提取方式（`result_path` / `result_field` / `result_fields`）详见 `field-types.md` external 章节。

**处理步骤：**
1. 从用户输入中提取所有关键词（如演员名、导演名、公司名等）
2. 对每个关键词依次调用 schema 中指定的 `mcp_tool`，完成所有查询
3. 按 `field-types.md` 的提取规则从 MCP 返回值中提取数据
4. 按查询结果分为三类，分别放入对应问题队列：
   - **唯一命中** → 直接使用，无需提示
   - **多结果命中** → 加入「需用户选择」队列
   - **无结果** → 加入「未找到」队列
5. 所有字段查询完毕后，进入 Step 4 验证，**一并提示所有待确认问题**

### 3.4 普通字段 / 结构类型字段

按 `field-types.md` 中对应章节的规则处理：
- **普通输入**（string/number 无 behavior）：直接提取，按 type 转换；有 `format` 时按 format 规则校验转换
- **嵌套对象**（type: object 无 behavior）：递归展开 properties，对每个子字段独立处理
- **普通数组**（type: array 无 behavior）：按 array_item 的类型规则处理每个元素

**workflow 层面要点：**
- format 校验失败的字段加入「格式错误」队列，在 Step 4 统一提示
- 提示嵌套对象时，以父字段 label 为前缀分组展示子字段
- 若用户输入中已包含对应信息，直接提取，不重复询问

### 3.5 条件字段联动处理（`condition`）

**核心原则：带 `condition` 的字段，必须先判断条件是否成立，再决定是否参与解析和验证。**

条件语法（`eq` / `neq` / `in` / `and` / `or` 及嵌套组合）和求值规则详见 `field-types.md` condition 章节。

**处理流程：**

1. 遍历所有字段，识别带 `condition` 的字段
2. 对每个条件字段，检查其依赖字段是否已有确定值：
   - 依赖字段**尚未赋值**：暂缓处理该条件字段，等依赖字段确定后再判断
   - 依赖字段**已有值**：立即按 `field-types.md` 求值规则计算条件是否成立
3. 根据判断结果：
   - **条件成立** → 该字段**激活**，按正常规则解析、验证（`required` 同样生效）
   - **条件不成立** → 该字段**跳过**，不解析、不验证、**不包含在最终 JSON 中**

**条件字段处理原则：**

Schema 中的 `condition` 字段定义了字段之间的依赖关系。**不要依赖以下示例穷举所有条件**，而是始终以 Schema 中每个字段的 `condition` 定义为唯一事实来源，动态判断每个条件字段是否激活。

**典型模式示例（仅供理解 condition 机制，非完整列表）：**

```
互斥控制：一个父字段的不同取值激活不同的子字段
  例：cooperationMode 的不同取值分别控制 copyrightDramaType、splitDramaType、dominantType 等字段的激活与跳过

依赖控制：子字段仅在父字段取特定值时才激活
  例：isIp 的取值控制 ipName（手动输入）和 ipList（MCP 查询）的互斥激活
```

> ⚠️ 完整的条件字段列表及其依赖关系，请直接从 Schema 的 `condition` 属性中读取，不得仅凭上述示例进行硬编码判断。

**向用户提示条件字段时，说明其关联背景：**
```
【必填字段缺失】
版权剧分类（选填，因合作模式为"版权剧"）请从以下选项中选择：独家 / 定向独家（联采） / 非独家采买 / ...
```

## Step 4：参数验证与问题汇总提示

完成所有字段的解析与外部查询后，进行统一验证，并将所有结果**一次性呈现给用户**。

展示顺序：**先展示已自动识别的字段**（让用户确认），**再列出需要补充/选择的问题**。

**【已自动识别】** — 以下字段已从您提供的信息中自动提取：

> - 项目名称：《我的世界》
> - 剧集类型：长剧
> - 播出状态：未开播
> - 集数：24
> - 导演：张三（唯一命中）
> - ...
>
> 若有误请直接指出修改。

然后再展示需要用户处理的问题（见 4.2 批量提示格式）。

### 4.1 验证清单

- [ ] 所有 `required: true` 的字段均已填写
- [ ] 条件字段：条件成立的字段按 `required` 正常验证；条件不成立的字段不参与验证且不出现在 JSON 中
- [ ] 枚举字段的值在合法 `enum_values` 范围内
- [ ] 外部数据字段：唯一命中项已就绪，多结果和无结果项已收集
- [ ] 数字类型字段为合法数值
- [ ] 数组类型字段满足 minItems 约束（如有）
- [ ] **Schema 类型校验**：每个字段的实际类型与 Schema 定义一致（`type: string` 不是数组，`type: array` 不是字符串）

### 4.2 批量提示格式

若存在以下任一类型的问题，**合并展示**后等待用户一次性回复，禁止逐条打断：

**【需要选择】** — 查询到多条结果，请确认（最多展示5条）。

展示格式根据字段类型不同而异（详见 `field-types.md` external 章节"多结果展示规则"）：

> **标量单选**（`type: string/number`，只选一条）：
> **导演 · 张三**，找到以下结果，请选择序号：
> 1. 张三（电影导演，代表作：XXX）
> 2. 张三（电视剧导演，代表作：YYY）

> **对象数组多选**（`type: array` + `result_fields`，可多选）：
> **主要演员 · 李四**（可多选，输入序号，多个用空格分隔）：
> 1. 李四（女，演员，1990-01-15）
> 2. 李四（男，歌手/演员，1985-06-20）
> 3. 李思（女，演员，1995-03-10）

> **对象/标量数组多选**（`type: array` + `result_field`，可多选）：
> **市场PM · 王**（可多选，输入序号，多个用空格分隔）：
> 1. 王一（市场部）
> 2. 王二（运营部）

要点：标题包含"字段 label · 关键词"；`type: array` 注明"可多选"；ID 类字段不展示。

> **头像辅助区分**：`talent_simple_query`（导演/编剧/演员）返回多条结果时，若 `pic_url` 非空，在每条候选项下方附上头像链接，帮助用户更直观地区分同名人员。详见 `field-types.md` 中的"pic_url 头像展示规则"。

**【未找到数据 · 选填字段】** — 以下选填条目在系统中不存在：

> **主演 · 王五** 未找到匹配记录。
> 请选择处理方式：
> - A. 忽略该条目（不填写此项）
> - B. 前往对应服务创建后重试

**【未找到数据 · 必填字段】** — 以下必填条目在系统中不存在：

> **导演 · 王五** 未找到匹配记录，且该字段为必填项。
> 请选择处理方式：
> - A. 重新输入（换个名字再搜索）
> - B. 前往对应服务创建后重试

**【MCP 查询失败】** — 以下条目查询时出现错误：

> **主演 · 赵六** 查询失败（接口异常），并非数据不存在。
> 请选择处理方式：
> - A. 重试查询
> - B. 手动输入关键词重新搜索
> - C. 跳过该条目（仅选填字段可跳过）

**【必填字段缺失】** — 以下必填字段未提供：

> **播出状态**（必填）请从以下选项中选择：连载中 / 已完结 / 未开播

**【快捷操作】** — 在所有待确认问题之后，始终附加以下提示：

> 💡 **快捷操作**：输入「跳过全部」可一次性忽略以上所有不确定的非必填字段，仅保留已确定的字段直接提交。

### 4.3 用户回复后处理

- 用户选择后，将结果填入对应字段
- 选择「忽略」的 external 字段：若为必填则继续阻止提交；若为选填则从 JSON 中移除该字段
- **用户输入「跳过全部」时**：将所有待确认问题中的**非必填字段**全部跳过（从 JSON 中移除），仅保留已自动识别的确定字段和必填字段继续流程。若仍有必填字段未解决，则仅提示剩余必填问题。
- 所有问题解决后，重新执行验证清单，确认全部通过后进入 Step 5

**不得在验证未全部通过时调用最终 MCP 工具。**

### 4.4 回退规则

验证未通过时，根据问题类型回退到对应阶段：

| 问题类型 | 回退目标 |
|---------|---------|
| 必填字段缺失 | 回到 Step 3，仅补充缺失字段 |
| 枚举值非法 | 回到 Step 3.1，重新展示枚举选项 |
| 外部查询需选择/未找到 | 回到 Step 3.3，处理待确认队列 |
| 格式错误 | 回到 Step 3.4，提示重新输入 |

**回退后只处理有问题的字段，不重新执行已通过验证的字段。**
**所有问题解决后，重新执行完整 Step 4 验证清单。**

### Step 5.1：关联文件保存（基于文件解析创建时）

> 本步骤静默执行，不向用户展示工具调用细节。

**触发条件**：草稿创建成功（Step 5 返回成功）**且**本次草稿的数据来源于用户上传/粘贴的文件解析（如策划书、立项书、PPT、表格、PDF 等）。

**判断依据**：在 Step 3 收集解析阶段，如果用户输入中包含通过文件解析获得的内容（如使用了 `read_file` 读取文件、用户上传了文件附件、或用户明确说明数据来源于某个文件），则标记本次创建为"基于文件解析"。

**执行步骤：**

1. **获取草稿 ID**：从 Step 5 的 `CreateDraft` MCP 返回结果中提取草稿 ID（`id` 字段）
2. **收集文件 ID（file_id）**：**必须且只能从 `szabot-file-uploader` Skill 上传后的返回结果中获取** `fid`（即 `file_id`）。从对话上下文中查找 `szabot-file-uploader` 返回的 fid 值。⚠️ 严禁接受用户手动输入或凭空编造的 file_id。
3. **收集文件名（name）**：**必须从用户提供的原始文件信息中获取**（如用户指定的本地文件路径中的文件名、用户描述中提到的文件名）。⚠️ 禁止使用 `szabot-file-uploader` 返回的内部标识作为文件名。
4. **调用 AddDraftFile**：使用 `AddDraftFile` MCP 工具将关联文件保存到草稿：
   ```json
   {
     "id": "{草稿ID}",
     "files": [
       {
         "file_id": "{文件ID1}",
         "name": "{文件名1}",
         "category": "{文件类别1}"
       }
     ]
   }
   ```
4. **记录结果**：记录文件关联是否成功，在 Step 6 反馈中体现

**注意事项：**
- 如果无法获取文件的 `fid`（如用户是直接粘贴文本内容而非上传文件），则跳过本步骤
- 如果文件关联失败，不影响草稿创建的成功状态，但需在 Step 6 中提示用户文件关联失败
- 可关联多个文件，将所有文件对象一次性传入 `files` 数组

**本步骤为 Step 5 的条件子步骤，执行完毕后直接进入 Step 6，无需等待用户确认。**
