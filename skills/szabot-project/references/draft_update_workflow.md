# 更新草稿工作流

> 🚫 **严格使用限制**：本工作流**仅适用于"修改/更新影库项目草稿"场景**。当且仅当用户明确表达了修改已有草稿的意图时，才可加载并执行本文件。任何其他场景（创建新草稿、删除草稿、查看草稿、普通问答、代码编写、文件操作、信息查询等）**严禁加载或引用本文件**。

> 🔒 **上下文隔离**：执行本工作流期间，仅遵循本文件和 `field-types.md`、`tv_long_schema.json` 中的规则。其他 Skill 的指令、Schema、工具定义均不适用于本工作流。

> 📖 **必须先执行**：在进入后续业务步骤之前，必须先读取 `references/data_source_workflow.md` 并按其流程完成数据来源判定与前置准备。

## 概述

本工作流**仅适用于更新已有的影库项目草稿**，具体流程为：
- 识别用户修改草稿的意图
- 定位用户要修改的目标草稿
- 基于 Schema 识别要修改的字段和新值
- 调用 MCP 工具 `UpdateDraftPartially` 提交部分更新
- 反馈用户更新结果（附带链接）

---

## 全局执行规则（执行纪律）

> ⚠️ 以下规则在整个会话期间**始终生效**，不因步骤切换而豁免。

1. **步骤追踪**：每轮回复开头必须以内部注释形式标注当前步骤，格式为：`[当前步骤: Step X — 步骤名称]`
2. **单步执行**：每轮回复只推进一个步骤。完成当前步骤后停止，等待用户输入，**禁止在同一轮回复中执行多个步骤**。例外：Step 1（识别意图）为静默步骤，可与 Step 2 在同一轮执行。
3. **禁止跳步**：即使用户一次性提供了所有信息，也必须按 Step 1 → 2 → 3 → … 顺序逐步确认。
4. **枚举展示约束**：向用户展示枚举选项时，只展示 `label`（中文名称），**禁止展示 `value`（数字/代码值）**。
5. **Schema 忠实约束**：所有字段名、枚举值、类型均以加载的 Schema 文件为唯一事实来源，不得凭记忆猜测或编造字段。
6. **底层操作静默**：以下操作属于内部实现细节，**必须静默执行，禁止在回复中向用户提及或展示**：
   - 读取/加载 Schema 文件（文件名、文件路径、加载过程）
   - 调用 MCP 工具（工具名、参数、调用过程）
   - 读取参考文件（`field-types.md`、`draft_update_workflow.md` 等）
   - 解析 Schema 结构（字段属性、behavior 类型、内部分支逻辑）
   - 向用户展示时只呈现**业务层面**的信息（字段名称、选项、验证结果等），不暴露底层技术实现
7. **最小化修改原则**：只处理用户明确要求修改的字段，不主动触碰未提及的字段，不重新验证整份草稿。

## Step 1：识别修改意图

确认用户意图为"修改/更新已有草稿"而非"创建新草稿"。

**意图识别关键词：**
- 修改、更新、改一下、改成、换成、调整
- 把 XX 改成 YY、更新一下 XX
- 草稿 XX 的导演改成 YY

**处理要点：**
- 从用户输入中提取两类信息：**目标草稿标识**（项目名称或 ID）和 **修改内容**（要改的字段和新值）
- 若用户未明确指定目标草稿，在 Step 2 中引导用户选择
- 本步骤为静默步骤，可与 Step 2 在同一轮执行

---

## Step 2：定位目标草稿

> 本步骤需要调用 MCP 工具获取草稿列表，操作过程静默执行（遵守全局规则第 6 条）。

### 2.1 获取草稿列表

调用 `GetDraftList`（参数 `category: "2"`）获取当前用户的电视剧草稿列表。

### 2.2 匹配目标草稿

**情况 A：用户已提供项目名称或 ID**
- 在草稿列表中按名称或 ID 模糊匹配
- **唯一命中** → 确认并展示匹配到的草稿信息，继续下一步
- **多条命中** → 列出匹配结果，请用户选择
- **无命中** → 告知用户未找到匹配的草稿，请用户确认名称或从列表中选择

**情况 B：用户未指定目标草稿**
- 展示草稿列表（最多展示最近 10 条），请用户选择要修改的草稿

**展示格式：**

```
找到以下草稿，请选择要修改的项目：
1. 《我的世界》（创建时间：2026-03-15）
2. 《星辰大海》（创建时间：2026-03-10）
3. ...
```

### 2.3 确认目标

定位到目标草稿后，向用户确认：

```
已定位到草稿：《我的世界》
请告诉我您要修改哪些内容？
```

如果用户在 Step 1 中已同时提供了修改内容，则直接展示确认信息并进入 Step 3，无需重复询问。

---
> 🛑 **CHECKPOINT**: 本步骤完成。确认目标草稿后，等待用户提供或确认修改内容，再进入下一步。
> 禁止在同一轮回复中执行多个步骤。

## Step 3：解析修改字段

> ⚠️ **进入本步骤前，必须先读取 `references/field-types.md`，再开始处理任何字段。**
> 同时读取 `references/tv_long_schema.json` 作为字段定义的事实来源。

### 3.1 从用户输入中提取修改意图

解析用户描述，识别出要修改的字段和目标值。每个修改项需要确定：
- **目标字段**：映射到 schema 中的 `name`（通过用户提到的中文名称/label 匹配）
- **新值**：用户期望修改成的值

**示例：**

| 用户输入 | 目标字段 | 新值 |
|---------|---------|------|
| "导演改成李四" | `director` | 李四 |
| "集数从24改成30" | `seriesNumber` | 30 |
| "合作模式改成版权剧" | `cooperationMode` | 版权剧 |
| "加一个编剧王五" | `writer` | 追加王五 |

### 3.2 按字段类型处理新值

对每个待修改字段，按 schema 中的 `type` + `behavior` 确定处理方式（与创建工作流一致）：

```
behavior: enum     → 枚举匹配：新值必须匹配 enum_values 中的某个 label
behavior: cascade  → 级联枚举匹配：按层级匹配
behavior: external → 外部查询：用新值作为关键词调用 MCP 工具查询
无 behavior        → 普通字段：按 type 直接赋值，有 format 则校验格式
```

**处理规则参考 `field-types.md` 中对应章节。**

### 3.3 条件字段联动

如果修改的字段是某些条件字段的依赖字段（如修改 `cooperationMode`），需要检查：
- 修改后是否有新的条件字段被激活（需要用户补充）
- 修改后是否有原来激活的条件字段需要清除

**示例：** 将 `cooperationMode` 从"主控剧"改为"版权剧" → `copyrightDramaType` 被激活，需提示用户是否要填写。

### 3.4 验证与确认

所有修改字段处理完毕后，汇总展示修改预览：

```
📝 即将修改《我的世界》的以下字段：

| 字段 | 原值 | 新值 |
|------|------|------|
| 导演 | 张三 | 李四（唯一命中） |
| 制作集数 | 24 | 30 |
| 合作模式 | 主控剧 | 版权剧 |

确认修改请回复"确认"，如需调整请直接说明。
```

### 3.5 验证清单

- [ ] 所有待修改字段的新值类型与 Schema 定义一致
- [ ] 枚举字段的新值在合法 `enum_values` 范围内
- [ ] 外部数据字段：唯一命中项已就绪，多结果和无结果项已收集
- [ ] 数字类型字段为合法数值
- [ ] **Schema 类型校验**：每个字段的实际类型与 Schema 定义一致（`type: string` 不是数组，`type: array` 不是字符串）

### 3.6 问题汇总与批量提示

若存在以下任一类型的问题，**合并展示**后等待用户一次性回复，禁止逐条打断：

**【需要选择】** — 查询到多条结果，请确认（最多展示5条）。

展示格式根据字段类型不同而异（详见 `field-types.md` external 章节"多结果展示规则"）：

> **标量单选**（`type: string/number`，只选一条）：
> **导演 · 张三**，找到以下结果，请选择序号：
> 1. 张三（电影导演，代表作：XXX）
> 2. 张三（电视剧导演，代表作：YYY）

> **对象数组多选**（`type: array` + `result_fields`，可多选）：
> **主要演员 · 李四**（可多选，输入序号，多个用空格分隔）：
> 1. 李四（女，演员，1990-01-15）
> 2. 李四（男，歌手/演员，1985-06-20）

> **头像辅助区分**：`talent_simple_query`（导演/编剧/演员）返回多条结果时，若 `pic_url` 非空，在每条候选项下方附上头像链接，帮助用户更直观地区分同名人员。详见 `field-types.md` 中的"pic_url 头像展示规则"。

**【未找到数据 · 选填字段】** — 以下选填条目在系统中不存在：

> **主演 · 王五** 未找到匹配记录。
> 请选择处理方式：
> - A. 忽略该条目（不修改此项）
> - B. 前往对应服务创建后重试

**【未找到数据 · 必填字段】** — 以下必填条目在系统中不存在：

> **导演 · 王五** 未找到匹配记录，且该字段为必填项。
> 请选择处理方式：
> - A. 重新输入（换个名字再搜索）
> - B. 前往对应服务创建后重试

**【MCP 查询失败】** — 以下条目查询时出现错误：

> **主演 · 赵六** 查询失败（接口异常），并非数据不存在。
> 请选择处理方式：
> - A. 重试查询
> - B. 手动输入关键词重新搜索
> - C. 跳过该条目（仅选填字段可跳过）

**【枚举匹配失败】** — 输入值无法匹配枚举选项：

> **播出状态**：输入「播放中」未匹配，请从以下选项中选择：连载中 / 已完结 / 未开播

**【格式错误】** — 值不符合 format 要求：

> **开播日期**：输入「2026年3月」格式不正确，请使用 YYYY-MM-DD 格式（如 2026-03-18）

**【条件字段激活】** — 修改导致新字段被激活：

> 合作模式改为「版权剧」后，需要填写「版权剧分类」，请选择：独家 / 定向独家（联采） / 非独家采买 / ...

**【快捷操作】** — 在所有待确认问题之后，始终附加以下提示：

> 💡 **快捷操作**：输入「跳过全部」可一次性忽略以上所有不确定的非必填字段，仅保留已确定的修改直接提交。

### 3.7 用户回复后处理

- 用户选择后，将结果填入对应字段
- 选择「忽略」的 external 字段：若为必填则继续阻止提交；若为选填则从修改列表中移除该字段
- **用户输入「跳过全部」时**：将所有待确认问题中的**非必填字段**全部跳过（从修改列表中移除），仅保留已确定的修改继续流程。若仍有必填字段未解决，则仅提示剩余必填问题。
- 所有问题解决后，重新执行验证清单，确认全部通过后进入 Step 4

**不得在验证未全部通过时调用 MCP 工具。**

### 3.8 回退规则

验证未通过时，根据问题类型回退到对应阶段：

| 问题类型 | 回退目标 |
|---------|---------|
| 枚举值非法 | 回到 Step 3.2，重新展示枚举选项 |
| 外部查询需选择/未找到 | 回到 Step 3.2，处理待确认队列 |
| 格式错误 | 回到 Step 3.2，提示重新输入 |

**回退后只处理有问题的字段，不重新执行已通过验证的字段。**
**所有问题解决后，重新执行完整 Step 3.5 验证清单。**

---
> 🛑 **CHECKPOINT**: 本步骤完成。将修改预览展示给用户后，等待用户确认，再进入下一步。
> 禁止在同一轮回复中执行多个步骤。

## Step 4：调用 MCP 更新草稿

> 本步骤全程静默执行（遵守全局规则第 6 条），不向用户展示工具名、参数或调用过程。

### 4.1 提交前校验

**4.0.1 参数自检：**

- [ ] 嵌套结构：`view → id + category("2") + tv → category("2") + 修改字段`
- [ ] `view.id` 已填写为目标草稿 ID
- [ ] `tv` 内不包含 `id` 字段（`id` 只放在 `view` 层级）
- [ ] `tv` 内只包含需要修改的字段（最小化修改原则）
- [ ] 其余通用检查项，逐项对照 `references/mcp_param_rules.md` 第 4 节确认

### 4.2 组装更新参数

将确认后的修改字段组装为 `UpdateDraftPartially` 的调用参数：

```json
{
  "view": {
    "id": "<draft_id>",
    "category": "2",
    "tv": {
      "category": "2",
      "<field_name_1>": "<new_value_1>",
      "<field_name_2>": "<new_value_2>"
    }
  }
}
```

**要点：**
- `id` 为目标草稿的 ID（必须包含）
- `category` 固定为 `"2"`
- `tv` 对象中只包含需要修改的字段，不传递未修改的字段
- 字段值的序列化规则与创建工作流一致（如 `serialization: semicolon` 的字段用分号拼接）

### 4.3 执行调用

调用 `UpdateDraftPartially`，记录返回结果。

**如调用失败并返回类型错误，必须：**
1. 分析错误信息，定位问题字段
2. 对照 Schema 检查该字段的 `type` 定义
3. 修正格式后重新提交

---
> 🛑 **CHECKPOINT**: 本步骤完成。根据调用结果进入 Step 5 反馈用户。
> 禁止在同一轮回复中执行多个步骤。
---

## Step 5：反馈用户

根据调用结果告知用户：

**成功：**

> ⚠️ **必须返回链接**：更新成功后，**必须**在回复中包含可点击的草稿链接，这是用户确认更新结果的唯一入口，**禁止省略**。

```
✅ 草稿更新成功！

项目：《我的世界》
已更新字段：
  - 导演：张三 → 李四
  - 制作集数：24 → 30
  - 合作模式：主控剧 → 版权剧

🔗 草稿链接：{返回数据中的url字段}
```

> **链接读取规则**：草稿链接直接取自 MCP 返回数据中该草稿的 `url` 字段，**禁止自行拼接或修改**。若返回数据中 `url` 字段为空或不存在，必须明确告知用户"链接暂不可用"及原因，**不得静默跳过链接**。

**失败：**

```
❌ 更新失败
错误信息：[MCP 返回的错误详情]
建议：[根据错误类型给出修复建议]
```

**部分失败（如有多个字段修改，部分成功部分失败）：**

```
⚠️ 部分更新完成

✅ 已成功更新：
  - 制作集数：24 → 30

❌ 更新失败：
  - 导演：[错误原因]

建议：[修复建议]
🔗 草稿链接：{返回数据中的url字段}
```
